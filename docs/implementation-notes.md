# Заметки реализации этапа 1

## Уточнения design v1.2

- D1: миграции стартера изолированы в `reliable_messaging_schema_history`; прикладной Flyway сначала создаёт свою схему. Реализация: `ReliableMessagingAutoConfiguration`, `ReliableMessagingSchemaMigrator`.
- D2: V2 добавляет `claim_token`; ack и ошибка обновляют только текущую аренду. V1 сохранена без изменений.
- D3: порядкового номера внутри агрегата нет; `MessageMeta` содержит идентификатор, время, агрегат и координаты Kafka. `occurredAt` не заменяет монотонную бизнес-версию.
- D4: порядок не гарантируется, согласно ADR-3; устаревшее указание группировки пачки будет исправлено в design.
- D5: добавляются Prometheus и provisioning Grafana.

## Отклонения от пошагового плана

- Контейнеры тестов — Spring-биновые `@ServiceConnection`, а не общие JUnit-поля интерфейса. JUnit останавливал контейнер между классами, оставляя кешированный Spring-контекст с мёртвым DataSource. Spring теперь управляет одинаковым жизненным циклом контейнера и контекста (`support/Containers`).
- D6: `request.timeout.ms = min(sendTimeout - linger, 30s)`, поскольку Kafka требует `delivery.timeout.ms >= request.timeout.ms + linger.ms`. Для коротких таймаутов linger уменьшается. `max.block.ms` тоже ограничен, чтобы отсутствие метаданных не задерживало релэй на стандартные 60 секунд (`KafkaOutboxDispatcher`).
- D7 / TODO(design): reaper переводит истёкшую последнюю попытку в DEAD, остальные — в NEW. Без этого повторяющиеся падения между claim и ack обходят `max-attempts`, хотя план требует учитывать такие попытки (`OutboxRepository.reclaimExpired`). Архитектура claim/send/ack сохранена.
- Публикатор дополнительно проверяет наличие транзакционного ресурса именно своего DataSource: транзакция другого менеджера не должна превращать запись события в autocommit (`JdbcOutboxPublisher`).

- D8: искусственная задержка демо применяется к пачке с первой попыткой. Постоянная задержка 3s при аренде 2s не даёт подтверждению ни одной попытки сойтись и в итоге исчерпывает лимит; первая задержка воспроизводит поздний ack и дубли, а последующие попытки позволяют завершить восстановление (`demo.order.DemoConfiguration`).
- Проверка брокера читает до появления всех уникальных message_id: остановка после первых 300 сырых записей ошибочно считает допустимые дубли потерей (`KafkaTestSupport.readUnique`).
- Собственный продюсер учитывает `KafkaConnectionDetails` вместе с `KafkaProperties`, в том числе адрес, security protocol и SSL bundle (`KafkaOutboxDispatcher`).

- Проверка reaper закрывает первый настоящий Spring-контекст с зависшим воркером и запускает второй контекст; PostgreSQL живёт отдельно от обоих. Повторный прогон читает и сравнивает полный набор идентичностей сообщений, включая случай допустимых дублей.
- На локальных томах найден старый каркас с V1 стартера в общей истории Flyway. Для проверки чистого этапа сохранены SQL-дампы и пересозданы только тома проекта; переход живых баз со старой общей истории требует отдельного переноса истории, не автоматического repair.
- Общий генератор джиттера использует потокобезопасный `Random`, поскольку `RandomGenerator.getDefault()` не обещает безопасность при совместном использовании воркерами ([Java 21 RandomGenerator](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/random/RandomGenerator.html)). Инъекция `RandomGenerator` для воспроизводимых тестов сохранена.
- Истёкшая последняя аренда учитывается как DEAD и в счётчике published{result=dead}, и в WARN с message_id/last_error, а не только в гейдже; это проверяет `ReaperIT`.

## Открытые вопросы

- D7 перенесён в протокол design v1.2. Переход старых живых баз с общей истории Flyway на изолированную историю остаётся отдельной операцией с сохранением данных; автоматический перенос не реализован.
