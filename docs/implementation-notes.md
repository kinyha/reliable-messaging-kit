# Заметки реализации этапа 1

## Уточнения design v1.2

- D1: миграции стартера изолированы в `reliable_messaging_schema_history`; прикладной Flyway сначала создаёт свою схему. Реализация: `ReliableMessagingAutoConfiguration`, `ReliableMessagingSchemaMigrator`.
- D2: V2 добавляет `claim_token`; ack и ошибка обновляют только текущую аренду. V1 сохранена без изменений.
- D3: порядкового номера внутри агрегата нет; `MessageMeta` содержит идентификатор, время, агрегат и координаты Kafka. `occurredAt` не заменяет монотонную бизнес-версию.
- D4: порядок не гарантируется, согласно ADR-3; устаревшее указание группировки пачки исправлено в design v1.2.
- D5: добавлены Prometheus и provisioning Grafana.

## Отклонения от пошагового плана

- Контейнеры тестов — Spring-биновые `@ServiceConnection`, а не общие JUnit-поля интерфейса. JUnit останавливал контейнер между классами, оставляя кешированный Spring-контекст с мёртвым DataSource. Spring теперь управляет одинаковым жизненным циклом контейнера и контекста (`support/Containers`).
- D6: `request.timeout.ms = min(sendTimeout - linger, 30s)`, поскольку Kafka требует `delivery.timeout.ms >= request.timeout.ms + linger.ms`. Для коротких таймаутов linger уменьшается. `max.block.ms` тоже ограничен, чтобы отсутствие метаданных не задерживало релэй на стандартные 60 секунд (`KafkaOutboxDispatcher`).
- D7 (закрыто в design v1.2): reaper переводит истёкшую последнюю попытку в DEAD, остальные — в NEW. Без этого повторяющиеся падения между claim и ack обходят `max-attempts`, хотя план требует учитывать такие попытки (`OutboxRepository.reclaimExpired`). Архитектура claim/send/ack сохранена.
- Публикатор дополнительно проверяет наличие транзакционного ресурса именно своего DataSource: транзакция другого менеджера не должна превращать запись события в autocommit (`JdbcOutboxPublisher`).

- D8: искусственная задержка демо применяется к пачке с первой попыткой. Постоянная задержка 3s при аренде 2s не даёт подтверждению ни одной попытки сойтись и в итоге исчерпывает лимит; первая задержка воспроизводит поздний ack и дубли, а последующие попытки позволяют завершить восстановление (`demo.order.DemoConfiguration`).
- Проверка брокера читает до появления всех уникальных message_id: остановка после первых 300 сырых записей ошибочно считает допустимые дубли потерей (`KafkaTestSupport.readUnique`).
- Собственный продюсер учитывает `KafkaConnectionDetails` вместе с `KafkaProperties`, в том числе адрес, security protocol и SSL bundle (`KafkaOutboxDispatcher`).

- Проверка reaper закрывает первый настоящий Spring-контекст с зависшим воркером и запускает второй контекст; PostgreSQL живёт отдельно от обоих. Повторный прогон читает и сравнивает полный набор идентичностей сообщений, включая случай допустимых дублей.
- На локальных томах найден старый каркас с V1 стартера в общей истории Flyway. Для проверки чистого этапа сохранены SQL-дампы и пересозданы только тома проекта; переход живых баз со старой общей истории требует отдельного переноса истории, не автоматического repair.
- Общий генератор джиттера использует потокобезопасный `Random`, поскольку `RandomGenerator.getDefault()` не обещает безопасность при совместном использовании воркерами ([Java 21 RandomGenerator](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/random/RandomGenerator.html)). Инъекция `RandomGenerator` для воспроизводимых тестов сохранена.
- Истёкшая последняя аренда учитывается как DEAD и в счётчике published{result=dead}, и в WARN с message_id/last_error, а не только в гейдже; это проверяет `ReaperIT`.

## Открытые вопросы

- D7 перенесён в протокол design v1.2. Переход старых живых баз с общей истории Flyway на изолированную историю остаётся отдельной операцией с сохранением данных; автоматический перенос не реализован.

## Этап 2: методика и отклонения

- Первый baseline остановлен: Toxiproxy с квотой 0,25 CPU достигал 24,90% CPU уже при 500 rps,
  а order-service использовал 18,31%, PostgreSQL 13,73%. Такой стенд измерял ограничение proxy.
  Все исходные файлы сохранены в `perf-harness/results/excluded-proxy-quota/`, не попадают в сводку.
  Квота Toxiproxy увеличена до 2 CPU / 256 MiB; его CPU теперь снимается вместе с целевыми сервисами.
  Квоты приложения, PostgreSQL и Kafka не менялись. Новый baseline и его повтор снимаются целиком.
- Сквозной Timer начинается с `rm-occurred-at` до коммита заказа, заканчивается после коммита платежа.
  Точный timestamp PostgreSQL commit не добавлялся: это изменило бы протокол этапа 1.
- Рестарт Spring-контекста в Testcontainers дополнен реальным SIGKILL контейнера order-service
  в perf-проекте; fixture-триггер держит ack после отправки Kafka. Оба режима потоков проверяются.
- H4 исключена согласно плану этапа 2. Изменения autovacuum (V3) допускаются только после H5,
  а внутренние оптимизации и дефолты — после соответствующих профилей и повторных измерений.
- Во время baseline-300-r2 macOS перешла в сон: окно 180 s заняло 5970,61 s по wall-clock.
  Серия 300 rps перенесена в `results/excluded-host-sleep/` и перезапущена целиком; завершённая
  серия 100 rps до сна сохранена. `--only-rps` возобновляет целые конфигурации по три повторения.
  На macOS команды держат временную `caffeinate -i -s` assertion, а все окна нагрузки и профилей
  проверяются по wall/monotonic clock. Скачок ≥1 s или превышение окна более чем на 60 s
  исключает результат; положительная длительность сама по себе не доказывает полный прогон.
- H5 допускает три независимые реплики на отдельных Ubuntu 24.04 GitHub runners. Это собственная
  группа `gha-h5` с фиксированными image/commit/config/architecture; её CPU и latency не смешиваются
  с локальным ARM64 baseline. Коллектор требует все три полных окна 7200 s, 60 s прогрева,
  устойчивый входной поток и точную доставку. Результаты принимаются после загрузки всех артефактов.
- Первый GitHub perf-gate (`37925727274`) дошёл до нагрузки после успешной сборки, но не доказал
  отказ по p99: k6 UID 12345 не мог записать JSON в Linux bind mount владельца runner. Логи артефакта
  подтвердили `permission denied`; длительный H5 (`37925727023`) остановлен до окончания.
  k6 теперь запускается с UID/GID процесса harness. Следующая CI-проверка должна сохранить JSON
  и завершиться именно сравнением p99, а не ошибкой инфраструктуры.
- H2 и H3 запускаются в отдельных GitHub jobs: все конфигурации одной гипотезы последовательно
  измеряются на одной VM, по три полных окна 180 s после 60 s прогрева новой JVM. H2 дополнительно
  снимает три CPU/alloc/wall и JFR профиля виртуальных воркеров. Коллектор не принимает частичную
  сетку, потерю доставки или прерванное окно. Эти группы `gha-virtual`/`gha-matrix` не объединяются
  с локальной ARM64 базовой линией. Разные jobs не делят Docker, CPU или базы данных.
- Первый вызов полного профиля остановился на `Unrecognized option: --dot`, хотя help установленного
  asprof перечислял параметр. Форматирование имён не требуется для сбора: параметр удалён.
  Короткая проверка CPU/alloc/wall с настоящей нагрузкой сохранила ненулевые HTML и collapsed,
  включая `--total` для allocations. Она исключена из performance-данных. Полные профили снимаются
  заново; уже завершённые baseline, H2/H3 и H5 от этой ошибки не затронуты.
- Для virtual CPU/wall учитывается ограничение async-profiler: стек может оборваться на continuation
  barrier ([описание автора](https://github.com/async-profiler/async-profiler/discussions/1745)).
  Нулевую долю атрибутированных relay-кадров нельзя трактовать как нулевой CPU или отсутствие ожиданий.
  Pinning проверяется отдельными JFR событиями `jdk.VirtualThreadPinned` с порогом 1 ms и tracePinnedThreads.
