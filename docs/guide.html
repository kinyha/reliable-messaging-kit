01 · Суть

Что это и зачем

Reliable Messaging Kit — это Transactional Outbox и Idempotent Consumer, упакованные в Spring Boot стартер для связки PostgreSQL + Kafka. Подключаешь зависимость, меняешь kafkaTemplate.send(...) на outbox.publish(...) внутри своей транзакции, вешаешь одну аннотацию на слушатель. Дальше стартер гарантирует две вещи:

  • событие не теряется: ни при падении сервиса, ни при недоступности Kafka, ни при деплое посреди отправки;
  • дубль не даёт двойного эффекта: если сообщение пришло дважды, платёж всё равно создаётся один раз.

Это учебный проект. Похожие библиотеки уже существуют (раздел 11). Смысл не в том, чтобы обогнать их, а в том, чтобы сделать продакшен-версию паттерна своими руками и разобраться, где он ломается: блокировки Postgres, гарантии продюсера Kafka, падения посреди отправки, дубли. На этапе 2 добавятся замеры, сколько эта надёжность стоит в миллисекундах.

Одной фразой для лида

Стартер делает «сохранить в базу и отправить событие» одним неделимым действием. Его подключают зависимостью, и сервис перестаёт терять и дублировать события. Учебная цель — построить это самому и доказать поведение под сбоями.

Чтобы почувствовать разницу, «урони» процесс в разных местах. Нажми на пунктирную строку между шагами.

    02 · Практика

    «Это же пара строк»

    Минимальный outbox действительно пишется за десять минут:

    // в бизнес-транзакции
orders.save(order);
outboxRepo.save(new OutboxRow(event));

// фоновая отправка
@Scheduled(fixedDelay = 200)
@Transactional
void relay() {
    for (var row : outboxRepo.findNew()) {
        kafka.send(row.topic(), row.key(), row.payload()).get();
        row.markSent();
    }
}

    На одном инстансе, пока ничего не падает, это работает. Вот что происходит в проде и как это закрыто в стартере:

    Что случилосьЧто делает код вышеЧто делает стартер
    Сервис в трёх подахВсе три берут одни и те же строки: каждое событие уходит трижды или поды ждут друг друга на блокировкеFOR UPDATE SKIP LOCKED: каждый под берёт свою пачку, без лидера и координации
    Kafka отвечает 5 секундТранзакция открыта всё это время: держит соединение из пула, снапшот, мешает vacuumТри коротких шага: захват с коммитом → отправка вне транзакции → подтверждение отдельной транзакцией
    Под убит посреди пачкиЧасть строк ушла в Kafka, но не помечена; если блокировку заменить статусом, строки зависнут навсегдаАренда (locked_until) + reaper: зависшие строки через 30 с возвращаются в очередь
    Под «заснул» на GC дольше аренды и проснулсяПерезаписывает статус строки, которую уже обрабатывает другой подФенсинг: подтверждение проходит только с тем claim_token, с которым строку захватили
    Kafka лежит 10 минутКаждые 200 мс все поды долбят брокер; после подъёма приходит синхронная волнаЭкспоненциальная задержка со случайным разбросом; попытки разных строк не совпадают по времени
    Одно битое сообщениеПадает на каждом проходе вечно, засоряет логи и очередьПосле 12 попыток статус DEAD с last_error, метрика и алерт
    Через месяцМиллионы SENT, запрос выборки деградируетЧастичные индексы только по ожидающим строкам; фоновая очистка SENT старше 7 дней
    Что-то застрялоНикто не узнаетМетрики: размер очереди, возраст самого старого события, число DEAD
    ПолучательДубли всё равно приходят: двойное списаниеInbox: INSERT … ON CONFLICT DO NOTHING в той же транзакции, что и бизнес-эффект
    Кто-то вызвал publish без транзакцииСобытие пишется в autocommit отдельно от заказа: тот же баг, только тихийИсключение сразу при вызове, в том числе если транзакция открыта на другом DataSource

    Каждая строка правой колонки — тоже «пара строк». Но в сумме это около тысячи строк кода с местами, где ошибку не видно на тестах. Наш собственный дизайн это подтвердил: ревью версии 1.0 нашло баги в протоколе ещё до кода, а при реализации нашлось ещё два (reaper обходил лимит попыток, таймаут продюсера не учитывал linger.ms). Стартер — способ сделать это один раз и не повторять в каждом сервисе.

    03 · API

    Что видит разработчик

    Всё, что нужно сделать в сервисе. Код взят из демо-стенда.

    1. Зависимость и одна обязательная настройка

    // build.gradle.kts
implementation("dev.reliablemessaging:outbox-spring-boot-starter:0.1.0")

# application.yml
outbox:
  inbox:
    retention: 30d     # обязательно: без значения приложение не стартует

    Таблицы создаются сами при старте: у стартера свои миграции и своя таблица истории Flyway, поэтому они не конфликтуют с миграциями сервиса.

    2. Отправка события

    было

    @Transactional
public UUID place(...) {
    jdbc.update("insert into orders ...");
    kafkaTemplate.send("orders.v1",
        id.toString(), toJson(event));
    return id;
}

    стало

    @Transactional
public UUID place(...) {
    jdbc.update("insert into orders ...");
    outbox.publish(OutboxMessage.builder()
        .topic("orders.v1")
        .aggregate(new Aggregate("order", id.toString()))
        .payload(event)
        .build());
    return id;
}

    publish — это обычный INSERT в таблицу outbox_message в твоей же транзакции. Откатился заказ — откатилось событие. Ключ партиции Kafka всегда равен id агрегата, вызывающий код не может его перепутать.

    3. Приём события

    @IdempotentConsumer(name = "payment-on-order-placed")
@KafkaListener(topics = "orders.v1", groupId = "payment-service")
public void consume(OrderPlaced event, MessageMeta meta) {
    jdbc.update("insert into payments(order_id, amount) values (?, ?)",
                event.orderId(), event.total());
}

    Аннотация оборачивает метод в транзакцию, сначала пишет meta.messageId() в inbox_message, и если такой id уже был — выходит, не вызывая метод. MessageMeta собирается из заголовков Kafka: id сообщения, агрегат, время события, топик, партиция, оффсет.

    04 · Как работает

    Путь одного события через код

    Заказ создан в order-service, платёж должен появиться в payment-service. Вот что происходит по шагам и какой класс за это отвечает.

    1. Запись события вместе с заказом

      Сначала проверка: транзакция активна и открыта именно на том DataSource, куда пишет стартер. Иначе исключение. Потом один INSERT: payload и заголовки как jsonb, новый message_id (UUID). Если в приложении включён трейсинг, в заголовки добавляется текущий traceparent, и трейс продолжится через Kafka.

      JdbcOutboxPublisher, PayloadSerializer, TraceHeadersSupplier

    2. Захват пачки (claim)

      Воркер релэя одним SQL-оператором выбирает до 128 готовых строк, блокирует их со SKIP LOCKED, переводит в IN_FLIGHT, ставит срок аренды и свой токен, считает попытку и сразу коммитит. Транзакция длится миллисекунды.

      with picked as (
    select id from outbox_message
    where status in ('NEW','FAILED') and next_attempt_at <= now()
    order by next_attempt_at, id limit ? for update skip locked
)
update outbox_message m
   set status = 'IN_FLIGHT', locked_until = now() + ?::interval,
       claim_token = ?, attempts = m.attempts + 1
  from picked where m.id = picked.id returning m.*
      OutboxRelay.work → OutboxRepository.claim

    3. Отправка в Kafka вне транзакции

      Своим продюсером с acks=all и идемпотентностью. Вся пачка отправляется асинхронно, затем общий дедлайн send-timeout. Результат считается по каждой записи отдельно: часть пачки может уйти, часть нет. В заголовки кладутся rm-message-id, rm-aggregate-type, rm-aggregate-id, rm-occurred-at.

      KafkaOutboxDispatcher (за интерфейсом OutboxDispatcher)

    4. Подтверждение

      Отдельная короткая транзакция. Успешные строки → SENT одним UPDATE … WHERE id = ANY(?). Неуспешные → FAILED с новым временем попытки или DEAD, если попытки кончились. Каждое обновление содержит AND claim_token = ?: если строку уже перехватил другой под, обновится 0 строк, и это нормально.

      OutboxRepository.acknowledge, RetryBackoff

    5. Страховка: reaper

      Если под умер между шагами 2 и 4, строка осталась в IN_FLIGHT, и обычная выборка её не видит. Раз в 10 секунд reaper ищет строки с истёкшей арендой и возвращает их в NEW. Если это была последняя попытка — сразу в DEAD: иначе под, который каждый раз падает на одном сообщении, крутил бы его бесконечно.

      LeaseReaper → OutboxRepository.reclaimExpired

    6. Приём с дедупликацией

      Spring Kafka вызывает слушатель, аспект перехватывает вызов: транзакция → INSERT INTO inbox_message … ON CONFLICT DO NOTHING → если вставилось, вызвать метод → коммит. Если метод бросил исключение, откатывается и запись в inbox, и Kafka доставит сообщение снова. Оффсет коммитится после обработки, то есть at-least-once.

      IdempotentConsumerAspect → IdempotentExecutor → InboxRepository; MessageMetaArgumentResolver

    05 · Возможности

    Фишки стартера

    Одна строка вместо dual-write

    outbox.publish в своей транзакции. Вызов без транзакции или на чужом DataSource отклоняется сразу.

    Горизонтальное масштабирование

    Любое число подов разбирает одну таблицу параллельно через SKIP LOCKED. Лидер, ZooKeeper и координация не нужны.

    Не держит транзакцию на сеть

    Захват и подтверждение — короткие транзакции, отправка в Kafka между ними. Пул соединений и vacuum не страдают от медленного брокера.

    Переживает смерть пода

    Аренда + reaper возвращают зависшие строки. Фенсинг через claim_token не даёт «проснувшемуся» поду испортить чужой результат.

    Умные повторы

    Экспонента с джиттером: брокер после падения не получает синхронную волну. Лимит попыток работает даже если под падает на каждой.

    Наблюдаемая недоставка

    DEAD с текстом последней ошибки, метрика и алерт. Ни одно событие не исчезает молча.

    Идемпотентность одной аннотацией

    @IdempotentConsumer: проверка дубля и бизнес-эффект в одной транзакции. Выдерживает параллельную доставку одного сообщения.

    Метрики и трейсинг

    Очередь, возраст старейшего события, отправки, перехваты reaper, дубли на входе. Trace-контекст едет через outbox, и в Jaeger видно запрос целиком.

    Безопасная конфигурация

    Свои миграции с отдельной историей Flyway. Опасные сочетания настроек (таймаут ≥ аренды, нет inbox.retention) ломают старт, а не прод.

    Заменяемая доставка

    Отправка спрятана за OutboxDispatcher. Свой бин — и вместо Kafka-продюсера стоит что угодно, например CDC.

    07 · База

    Kafka и Postgres: что нужно для практики

    Kafka

    • Партиция и ключ. Топик разбит на партиции, партиция выбирается по хешу ключа. Порядок есть только внутри партиции. У нас ключ всегда равен id агрегата, поэтому все события заказа попадают в одну партицию.
    • acks=all. Продюсер считает запись успешной, только когда её подтвердили все синхронные реплики. acks=1 теряет данные, если лидер умер до репликации. В наивном режиме демо стоит именно acks=1.
    • Идемпотентный продюсер. Брокер отбрасывает дубль, если продюсер переотправил то же сообщение из-за сетевой ошибки. Работает только в пределах одной сессии продюсера: после рестарта процесса это уже другой продюсер. Поэтому дубли от релэя всё равно возможны, и их гасит inbox.
    • linger.ms. Продюсер копит сообщения в памяти, чтобы отправить пачкой. Всё, что лежит в буфере, умирает с процессом. Наивный режим демо держит linger.ms=1000, чтобы это было видно на kill -9.
    • At-least-once у потребителя. Spring Kafka коммитит оффсет после того, как слушатель вернул управление. Упал до коммита — сообщение придёт ещё раз.
    • Почему не exactly-once Kafka. Транзакции Kafka атомарны только внутри Kafka (прочитал → записал → закоммитил оффсет). Переход «коммит в Postgres → запись в Kafka» они не покрывают.

    PostgreSQL

    • FOR UPDATE живёт до конца транзакции. После коммита строка свободна. Поэтому блокировкой нельзя защитить отправку, которая идёт после коммита, и роль «занято» берёт статус IN_FLIGHT с арендой.
    • SKIP LOCKED. Заблокированные другим строки не ждём, а пропускаем. Два пода получают разные пачки.
    • Частичный индекс. WHERE status IN ('NEW','FAILED') в индексе: он остаётся крошечным, сколько бы ни было SENT. Планировщик возьмёт его, только если условие запроса совпадает с условием индекса. Тест IndexUsageIT проверяет это через EXPLAIN.
    • ON CONFLICT DO NOTHING при гонке. Вторая вставка того же ключа ждёт первую. Первая закоммитила — вторая получает конфликт; откатилась — вторая вставляет. Отсюда однократность при параллельной доставке.
    • MVCC и vacuum. Каждый UPDATE создаёт новую версию строки. Outbox обновляет каждую строку 3–4 раза, мёртвых версий много. Как с этим справляется autovacuum — вопрос этапа 2.

select id from outbox_message             select id from outbox_message

    Аналоги и зачем писать своё

    Первый вопрос лида будет «а почему не готовое». Готовое есть:

    РешениеКак устроеноОтличие от нас
    Spring Modulith, Event Publication RegistryХранит публикации событий в базе, умеет выгружать их во внешний брокер, повторяет незавершённыеБлиже всего по идее. Сторона получателя (inbox) не входит
    Debezium Outbox Event RouterCDC: читает WAL Postgres и пишет в Kafka через Kafka ConnectПриложение не участвует в отправке, но нужна отдельная инфраструктура; inbox не решает
    transaction-outbox (gruelbox)Java-библиотека: в транзакции сохраняет вызов, потом выполняет с повторамиУниверсальная, не заточена под Kafka; inbox свой
    Eventuate TramФреймворк транзакционного обмена сообщениями с CDC и дедупликациейЦелая платформа со своими сервисами

    Зачем тогда своё. Это IVP-проект на обучение. Готовую библиотеку можно подключить, не понимая, как она ведёт себя при падении пода. Написать свою и сломать её на стенде — способ это понять. Результат полезен и при наличии аналогов:

    • понимание и чек-лист того, что должна уметь любая outbox-реализация (раздел 02), чтобы оценивать готовые решения;
    • стенд со сценариями сбоя, на котором можно проверить любую реализацию, включая готовую;
    • замеры цены надёжности на этапе 2, которых обычно нет в README библиотек;
    • рабочий стартер для сервиса, где тянуть Modulith или Debezium избыточно.

    Честно и полезно сказать на демо: «если в команде уже есть Debezium или Spring Modulith, вот как сравнить их с этим чек-листом».

    14 · Подготовка

    Вопросы, которые зададут после демо

    Почему не отправить в Kafka в afterCommit?

    Это тот же dual-write: между коммитом и отправкой процесс может умереть, а сообщение в буфере продюсера живёт только в памяти. Наивный режим демо устроен именно так, и kill -9 показывает потерю.

    Почему не Debezium или Spring Modulith?

    Цель проекта — разобраться и измерить, а не заменить их. Debezium требует Kafka Connect и не решает inbox; Modulith ближе всего, но тоже без стороны получателя. Наш чек-лист и стенд подходят, чтобы проверить любое из этих решений. Сама отправка у нас за интерфейсом OutboxDispatcher, её можно заменить на CDC.

    Что будет, если под умрёт, держа пачку?

    Строки останутся в IN_FLIGHT. Через 30 с (аренда) reaper вернёт их в NEW, и другой под отправит. То, что уже успело уйти в Kafka, придёт дублем и будет отброшено inbox.

    Зачем claim_token, если есть locked_until?

    locked_until говорит, когда аренда истекает, но не говорит, чья она. Под, проснувшийся после долгой паузы, должен понять, что строка уже не его. Токен — это идентификатор конкретного захвата.

    Почему порядок не гарантирован, если ключ партиции один?

    Ключ определяет партицию, а не момент отправки. Повтор упавшего события уходит позже следующего. Строгий порядок требует сериализации по агрегату (advisory lock), это рассмотрено и отвергнуто как слишком дорогое.

    Что если вызвать publish без транзакции?

    IllegalTransactionStateException сразу. И если транзакция открыта, но на другом DataSource, тоже исключение: иначе запись тихо ушла бы в autocommit отдельно от заказа.

    Какой inbox.retention ставить?

    Не меньше retention топика плюс глубина replay, которую вы допускаете. Удалишь запись раньше — переигранное сообщение пройдёт как новое.

    Не распухнет ли таблица outbox?

    RetentionCleaner удаляет SENT старше 7 дней батчами. DEAD не удаляется никогда. Индексы частичные, поэтому выборка не замедляется с ростом истории. Поведение autovacuum под нагрузкой — тема этапа 2.
