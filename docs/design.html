v1.1Changelog

Что изменилось в версии 1.1

Версия 1.0 прошла ревью, которое нашло семь дефектов спецификации. Все они закрыты здесь — до начала реализации, потому что четыре из них относятся к протоколу параллелизма и к формулировкам гарантий, а такие ошибки в коде обходятся дороже всего.

  • Протокол релэя расписан по тактам (§ 6). Блокировка FOR UPDATE не может защищать сетевой вызов, поэтому захват коммитится до публикации, а роль «занято» берёт статус IN_FLIGHT с арендой. Добавлен reaper и отдельный индекс под него.
  • Обещание порядка отозвано (ADR‑3). Прежнее решение было неверным; теперь порядок не гарантируется, а требование коммутативности обработчиков объявлено явно.
  • ADR‑5 про bloom-фильтр удалён и заменён на честный горячий путь дедупликации: один INSERT … ON CONFLICT DO NOTHING без предварительной проверки.
  • Критерий готовности исправлен (§ 8): дубликаты воспроизводятся намеренно, однократен бизнес-эффект — прежняя формулировка противоречила выбранной at-least-once семантике.
  • У inbox.retention убран небезопасный дефолт (§ 7): слишком короткий срок ломает дедупликацию при replay.
  • Границы однократности вынесены к API потребителя (§ 7): внешние вызовы за пределами транзакции однократными не становятся.
  • Формулировка DEAD исправлена (§ 6): durable intent и наблюдаемая недоставка вместо «гарантированной доставки».

Кроме того, язык реализации зафиксирован как Java, а оценка часов приведена к фактическому бюджету проекта.

§ 1Результат

Что именно является результатом

Результат — не сервис. Сервис нельзя переиспользовать, его можно только эксплуатировать. Результат — библиотека и стенд, на котором она доказывает свои свойства. Три артефакта, каждый со своей ролью на защите:

АртефактЧто это техническиРоль
outbox-spring-boot-starter Gradle-модуль, публикуется в внутренний Nexus. Автоконфигурация, Flyway-миграции таблиц, API публикации, фоновый релэй, метрики Micrometer. Главный продукт. Это то, что «могут использовать другие без автора».
demo-stand order-service → Kafka → payment-service, docker-compose с Postgres, Kafka, Jaeger, Grafana. Скрипты сценариев сбоя. Полигон. Сам по себе ценности не несёт — существует, чтобы стартер было на чём ломать.
perf-harness k6-сценарии, JMH-бенчмарки, Toxiproxy-профили сбоев, GitHub Actions workflow с порогами по p99. Этап 2. Превращает утверждения о надёжности и скорости в числа.

Граница проведена так: всё, что знает про ваш бизнес-домен, живёт в demo-stand; всё, что универсально, живёт в стартере. Если в стартер просачивается слово «order» — граница нарушена.

На защите спросят

«А почему не готовое решение?» Ответ: Debezium решает половину задачи (доставку из БД), но не решает идемпотентность на стороне потребителя и требует отдельной инфраструктуры. См. § 5, ADR‑1.

§ 2Проблема

Задача: dual-write не бывает атомарным

Сервис делает две вещи, которые обязаны произойти вместе: меняет состояние в своей базе и сообщает об этом остальным через Kafka. Два разных хранилища, две разные транзакции, общей транзакции между ними не существует. Между коммитом и отправкой есть окно, в котором процесс может умереть.

Симметричная беда — если поменять шаги местами: событие ушло, транзакция откатилась, потребители обработали заказ, которого нет. Обе перестановки неверны, потому что неверна сама идея двух независимых записей.

Формулировка задачи

Дать сервису способ атомарно зафиксировать изменение состояния вместе с намерением отправить событие, доставлять это намерение с повторами до подтверждения — и сделать так, чтобы повторная доставка не меняла результат. Обратите внимание на формулировку: система гарантирует не однократную доставку, а однократный эффект, и только для изменений в той же базе.

§ 3Архитектура

Решение: outbox на стороне отправителя, inbox на стороне получателя

Ключевой ход — убрать вторую запись. Вместо «записать в БД и отправить в Kafka» сервис делает одну запись в БД: и бизнес-строку, и строку в таблицу outbox_message, в одной транзакции. Отправка становится отдельной, асинхронной, повторяемой операцией, которую выполняет релэй, читая уже закоммиченные строки.

Правая половина схемы так же важна, как левая. Релэй гарантирует at-least-once: если он упал между отправкой в Kafka и обновлением статуса, событие уйдёт повторно. Поэтому потребитель обязан быть идемпотентным — это не опциональная добавка, а вторая половина того же решения. Таблица inbox_message хранит идентификаторы уже обработанных сообщений.

Тонкость

Запись в inbox_message и бизнес-эффект обработчика должны быть в одной транзакции. Иначе дедупликация повторяет ровно тот баг, который мы чиним, только на стороне получателя.

§ 4Данные

Модель данных

Схема создаётся Flyway-миграциями, которые едут внутри стартера. Пользователь библиотеки не пишет DDL руками — иначе тиражируемость страдает на первом же подключении.

-- сторона отправителя
create table outbox_message (
    id                bigserial    primary key,
    message_id        uuid         not null unique,
    aggregate_type    text         not null,
    aggregate_id      text         not null,
    topic             text         not null,
    partition_key     text         not null,
    payload           jsonb        not null,
    headers           jsonb        not null default '{}',
    status            text         not null default 'NEW',
    attempts          int          not null default 0,
    created_at        timestamptz  not null default now(),
    next_attempt_at   timestamptz  not null default now(),
    locked_until      timestamptz,
    sent_at           timestamptz,
    last_error        text,
    constraint outbox_message_status_check
        check (status in ('NEW','IN_FLIGHT','FAILED','SENT','DEAD'))
);

-- частичный индекс: то, что ждёт отправки
create index outbox_pending_idx
    on outbox_message (next_attempt_at, id)
    where status in ('NEW', 'FAILED');

-- reaper: строки, захваченные подом, который умер, не дойдя до ack
create index outbox_expired_lease_idx
    on outbox_message (locked_until, id)
    where status = 'IN_FLIGHT';

-- сторона получателя
create table inbox_message (
    message_id   uuid        not null,
    consumer     text        not null,
    processed_at timestamptz not null default now(),
    primary key (message_id, consumer)
);

Три решения в этой схеме стоит проговорить отдельно, потому что каждое из них — компромисс.

Частичный индекс вместо полного

Отправленные строки — это 99,9 % таблицы через неделю работы. Индекс с условием where status in ('NEW','FAILED') остаётся крошечным независимо от объёма истории, потому что B-tree физически не содержит строк, не подходящих под предикат. Планировщик использует его только если условие запроса логически влечёт предикат индекса — это надо проверить через EXPLAIN, а не предположить.

Составной первичный ключ в inbox

Одно и то же событие может обрабатываться несколькими независимыми потребителями в одном сервисе. Ключ (message_id, consumer) позволяет каждому вести свой учёт; ключ только по message_id заставил бы первого потребителя «съесть» сообщение у остальных.

payload как jsonb, а не bytea

jsonb даёт возможность посмотреть глазами, что застряло в очереди, и построить индекс по полю при разборе инцидента. Цена — потеря байтовой точности исходного представления и невозможность хранить Avro/Protobuf как есть. Для стартера, который прежде всего должен быть отлаживаемым, это правильный размен; в конфигурации оставим переключатель.

Что померить на этапе 2

Раздувание таблицы и autovacuum. Outbox — это таблица с высоким churn: строки живут минуты и умирают. Классическое место, где HOT-updates и настройки autovacuum решают всё. Отличный материал для второго демо.

§ 5Решения

Архитектурные решения

Пять развилок, каждая с зафиксированным выбором и честной ценой. Это тот раздел, из которого берутся ответы на вопросы после демо.

ADR‑1

Релэй встроен в приложение, а не вынесен в отдельный сервис

Принято

Outbox-таблица физически принадлежит базе конкретного сервиса. Вопрос — кто её читает.

Рассмотрены
A. Встроенный релэй — библиотека поднимает фоновые воркеры в том же процессе. B. Отдельный релэй-сервис — один общий деплой обслуживает все outbox-таблицы компании. C. CDC через Debezium — читает WAL Postgres и льёт изменения в Kafka без участия приложения.
Выбрано
A, с оговоркой. Вариант B требует, чтобы посторонний сервис знал схему и имел доступ к чужой БД — это shared database, разрушение границы владения данными и вечный источник несовместимых миграций. Вариант C архитектурно самый чистый и самый производительный, но добавляет Debezium и Kafka Connect в инфраструктуру, работает на уровне строк таблицы, а не доменных событий, и не решает половину задачи — идемпотентность потребителя.
Цена
Релэй конкурирует за ресурсы с обработкой запросов в том же JVM. Именно поэтому этап 2 начинается с вопроса «сколько процессорного времени и латентности релэй отъедает у бизнес-эндпоинтов» — это измеримо, и это будет измерено.
Оговорка
Публикация выносится за интерфейс OutboxDispatcher. Если на этапе 2 числа скажут, что встроенный релэй мешает, реализация меняется на CDC без изменения кода на стороне приложения.
ADR‑2

Опрос через SKIP LOCKED вместо выбора лидера

Принято

Сервис работает в нескольких подах. Все они видят одну outbox-таблицу — нужно, чтобы они не отправляли одно и то же дважды и не простаивали.

Выбрано
SELECT … FOR UPDATE SKIP LOCKED LIMIT :batch внутри короткой транзакции захвата. Строки, заблокированные другим подом, не попадают в выборку — вместо ожидания транзакция их пропускает. Никакого leader election, никакого ZooKeeper, никакой пассивной реплики.
Важное уточнение (v1.1)
Блокировка FOR UPDATE живёт ровно до конца транзакции и потому не может защищать публикацию в Kafka — сетевой вызов происходит уже после коммита. Роль «эта строка занята» после коммита берёт на себя не блокировка, а статус IN_FLIGHT вместе с locked_until. Полный протокол — в § 6.
Альтернатива
Advisory lock на весь релэй: работает один под, остальные ждут. Проще рассуждать о порядке, но пропускная способность не масштабируется и переключение при падении лидера занимает время удержания блокировки.
Цена
Глобальный порядок отправки теряется. Строка 105 может уйти раньше строки 104, если их забрали разные поды — см. ADR‑3.
ADR‑3

Порядок событий не гарантируется; обработчики обязаны быть коммутативными

Пересмотрено в v1.1

Версия 1.0 обещала порядок внутри агрегата. Обещание было неверным и здесь отзывается.

Почему прежнее решение не работало
Один partition_key гарантирует, что события агрегата попадут в одну партицию Kafka — но не то, в каком порядке они туда попадут. Между созданием строки и публикацией стоит релэй, работающий в нескольких подах. Предложенная в v1.0 «группировка пачки по ключу» дыру не закрывает: повтор упавшего события уходит позже, чем уже захваченное следующее, и обгон происходит даже внутри одного пода.
Выбрано
Порядок доставки не гарантируется. Обработчики обязаны быть коммутативными: результат не зависит от порядка применения событий. Стартер помогает это соблюсти, передавая в обработчик occurred_at и порядковый номер события внутри агрегата, чтобы устаревшее событие можно было распознать и отбросить.
Отвергнуто
Строгий порядок через advisory lock по хешу aggregate_id плюс монотонный sequence: под захватывает агрегат целиком и держит его, пока не отправит все накопленные события. Работает, но вводит single-flight на агрегат — точку сериализации — и заметно усложняет reaper. Для этого проекта цена выше пользы; вариант описан здесь, чтобы предъявить его на защите как рассмотренный.
Цена
Потребитель, которому порядок действительно нужен, отбрасывает устаревшие события сам, сравнивая порядковый номер с уже применённым. Ограничение выносится в README отдельным абзацем, а не прячется в примечании.
ADR‑4

At-least-once плюс идемпотентность вместо exactly-once

Принято

У Kafka есть транзакции и exactly_once семантика. Она не решает нашу задачу, и это стоит понимать точно.

Что даёт Kafka EOS
Атомарность между чтением из Kafka, обработкой и записью обратно в Kafka. То есть внутри границ Kafka. Наша транзакция пересекает границу Postgres ↔ Kafka, и туда EOS не дотягивается.
Следствие
Дубликаты неизбежны, и попытки их избежать — потерянное время. Правильная цель — сделать дубликат безвредным. Отсюда inbox-таблица, отсюда требование к обработчику быть идемпотентным, отсюда message_id как сквозной идентификатор.
ADR‑5

Дедупликация — один INSERT, без предварительной проверки

Заменяет ADR‑5 из v1.0

В версии 1.0 здесь стоял bloom-фильтр перед обращением к inbox-таблице. Решение было технически неверным и удалено целиком.

Почему bloom не подходит
Даже когда фильтр отвечает «точно не видели», вставить message_id в inbox всё равно необходимо — и в той же транзакции, что и бизнес-эффект, иначе следующий дубликат пройдёт насквозь. Значит обращение к БД происходит при любом ответе фильтра, и экономить нечего. Вдобавок в нескольких подах фильтры расходятся, а периодическая пересборка создаёт окно, в котором фильтр пуст.
Выбрано
Горячий путь — ровно один INSERT INTO inbox_message … ON CONFLICT DO NOTHING в транзакции обработчика. Ноль затронутых строк означает «уже обрабатывали» и приводит к раннему выходу. Предварительного SELECT в коде нет вообще: проверка и захват — одна операция, гонки между ними не существует.
Что настраивать вместо этого
Реальный рычаг производительности здесь — не структура в памяти, а размер и обслуживание таблицы: retention, партиционирование по processed_at при больших объёмах, autovacuum. Это и проверяется замерами на этапе 2.
§ 6Поведение

Жизненный цикл сообщения и обработка отказов

Строка outbox проходит конечное число состояний. Явная модель состояний — не бюрократия: без неё невозможно ответить на вопрос «что происходит, если под умер, удерживая пачку».

Протокол релэя: три такта

Это место, где версия 1.0 была неполной. Наивное «взять строки под FOR UPDATE и отправить их» не работает, потому что блокировка живёт до конца транзакции: держать транзакцию открытой на время сетевого вызова в Kafka означало бы долгие транзакции, распухание снапшотов и остановку autovacuum. Поэтому такт захвата и такт публикации разделены.

  1. Захват. Короткая транзакция: SELECT … FOR UPDATE SKIP LOCKED LIMIT :batch, затем UPDATE отобранных строк в IN_FLIGHT с locked_until = now() + lease, затем commit. Блокировка снимается, но строка помечена как занятая.
  2. Публикация. Вне транзакции, с уже закоммиченной пачкой на руках. Здесь происходит сетевой вызов, который может занять секунды или не завершиться вовсе.
  3. Подтверждение. Отдельная короткая транзакция: успешные строки переводятся в SENT, неуспешные — в FAILED с увеличением attempts и новым next_attempt_at.

Между вторым и третьим тактом процесс может умереть. Тогда строка остаётся в IN_FLIGHT навсегда — и её никто не подберёт, потому что основной индекс покрывает только NEW и FAILED. Ровно поэтому нужен reaper: отдельный проход возвращает в NEW строки со статусом IN_FLIGHT и истёкшим locked_until, опираясь на свой индекс outbox_expired_lease_idx. Без него сообщения молча застревают — это самый неприятный из возможных отказов, потому что он не проявляется ни ошибкой, ни ростом очереди.

Цена протокола — расширение окна дубликатов: событие, отправленное в Kafka и не подтверждённое в базе, уйдёт повторно. Это ожидаемо и безвредно, потому что потребитель идемпотентен.

Экспоненциальная задержка с джиттером

При недоступности Kafka все воркеры всех подов упрутся одновременно. Без джиттера они и повторять начнут одновременно, создавая синхронизированные волны нагрузки на восстанавливающийся брокер — так падают уже поднявшиеся кластеры. Случайное рассеивание задержки убирает синхронизацию.

DLQ — это решение продукта, а не техники

Стоит назвать вещи своими именами: система даёт не «гарантированную доставку», а durable intent — намерение, которое переживёт перезапуск, — плюс повторы и наблюдаемую недоставку. Строка в DEAD означает, что событие не будет доставлено без вмешательства человека. Стартер обязан кричать об этом: метрика, алерт, и last_error в таблице. Тихое умирание сообщений хуже, чем исходный баг, потому что создаёт ложное чувство надёжности.

Демо-момент

Сценарий «Kafka лежит 5 минут» на демо смотрится лучше всего: видно, как растёт очередь, как работает backoff, и как после подъёма брокера всё дренируется без потерь.

§ 7API

Публичный интерфейс стартера

Критерий качества API здесь простой: сколько строк должен написать разработчик, чтобы перестать терять события. Цель — одна.

// сторона отправителя — публикация внутри существующей транзакции
@Service
public class OrderService {

    private final OrderRepository orders;
    private final OutboxPublisher outbox;

    public OrderService(OrderRepository orders, OutboxPublisher outbox) {
        this.orders = orders;
        this.outbox = outbox;
    }

    @Transactional
    public OrderId placeOrder(PlaceOrder cmd) {
        Order order = orders.save(Order.from(cmd));

        outbox.publish(OutboxMessage.builder()
                .topic("orders.v1")
                .aggregate(new Aggregate("order", order.id().toString()))
                .payload(new OrderPlaced(order.id(), order.total(), order.customerId()))
                .build());

        return order.id();
    }
}

OutboxMessage.partitionKey() всегда возвращает aggregate.id: обязательный ключ партиции вычисляется самим стартером и не может разойтись с идентификатором агрегата. Никакого KafkaTemplate, никаких колбэков на коммит транзакции, никаких TransactionSynchronization. Вызов publish — это обычный INSERT, он либо откатится вместе с заказом, либо переживёт его.

// сторона получателя — идемпотентность через аннотацию
@Component
public class PaymentListener {

    private final PaymentService payments;

    public PaymentListener(PaymentService payments) {
        this.payments = payments;
    }

    @IdempotentConsumer(name = "payment-on-order-placed")
    @KafkaListener(topics = "orders.v1")
    public void on(OrderPlaced event, MessageMeta meta) {
        payments.reserve(event.orderId(), event.total());
    }
}

Аннотация оборачивает вызов: открывает транзакцию, пытается вставить message_id в inbox, при конфликте уникальности молча выходит, иначе вызывает метод и коммитит всё вместе. Проверка и бизнес-эффект оказываются в одной транзакции — то самое требование из § 3.

Где однократность заканчивается

Эффект применяется один раз только для изменений в той же транзакции PostgreSQL, что и запись в inbox. Всё, что обработчик делает за пределами этой транзакции, однократным не становится: HTTP-вызов платёжного провайдера, запись в другую базу, отправка письма, публикация в другой топик. При повторной доставке транзакция откатится, а внешний вызов — нет.

Для таких случаев нужна идемпотентность на стороне получателя вызова — ключ идемпотентности в API провайдера — или отдельная запись о факте вызова в той же транзакции, с последующей сверкой. Стартер эту задачу не решает и не притворяется, что решает.

Конфигурация

outbox:
  relay:
    enabled: true
    workers: 2              # воркеров на под
    batch-size: 128
    poll-interval: 200ms
    lease-duration: 30s
    max-attempts: 12
  cleanup:
    retention: 7d           # отправленные строки живут неделю
  inbox:
    # обязателен и без дефолта: значение должно быть не меньше
    # максимального окна повторной доставки и ручного replay
    retention: 30d

У inbox.retention намеренно нет значения по умолчанию. Слишком короткий срок незаметно ломает дедупликацию: после сброса оффсетов потребителя Kafka переиграет старые сообщения, записи о которых уже вычищены, и бизнес-эффект применится второй раз. Безопасного универсального значения не существует — оно зависит от retention топика и от того, насколько глубокий replay считается допустимым, — поэтому стартер отказывается стартовать, пока значение не задано явно.

Проверка на защите

Хороший вопрос себе: что произойдёт, если разработчик вызовет outbox.publish вне транзакции? Правильный ответ — исключение при старте вызова, а не тихая отправка. Явный отказ лучше молчаливой поломки инварианта.

§ 8Этап 1

Этап 1 — построить и доказать корректность

Месяц первый. Задача этапа — получить работающий стартер и доказать, что заявленная гарантия соблюдается под сбоями. Производительность на этом этапе не измеряется вообще: сначала правильно, потом быстро.

Объём работ

  • Модуль стартера: автоконфигурация, Flyway-миграции, OutboxPublisher, OutboxRelay на SKIP LOCKED.
  • Ретраи с экспоненциальной задержкой и джиттером, DLQ, метрики Micrometer (глубина очереди, возраст старейшего неотправленного, счётчики попыток).
  • @IdempotentConsumer и inbox-таблица.
  • Демо-стенд: два сервиса, docker-compose, скрипты нагрузки и сценариев сбоя.
  • Интеграционные тесты на Testcontainers, в том числе тест на конкурентный захват пачки несколькими релэями.
  • README: подключение за пять минут, описание гарантий и их границ.

Критерии готовности

ПроверкаОжидаемый результат
Убить приложение kill -9 под нагрузкой 500 rpsЧисло заказов в БД равно числу событий, дошедших до потребителя. Расхождение — ноль.

Сценарий демо

Пятнадцать минут, из них десять — живой показ. Порядок такой: сначала запускается стенд с выключенным outbox — наивный dual-write, — под нагрузкой убивается процесс, и на экране видно расхождение счётчиков. Затем то же самое с включённым стартером: расхождение ноль. Дальше — падение Kafka и дренаж очереди на графике Grafana. Заканчиваем трейсом в Jaeger, где виден путь одного события целиком.

Главный приём этой защиты: не рассказывать про надёжность, а сломать систему на глазах у зала и показать, что она выжила. Слайд с архитектурой при этом нужен ровно один.

Риск этапа

Соблазн сделать «ещё фич» — приоритеты сообщений, батчинг, поддержку RabbitMQ. Всё это вне рамок. Этап 1 закрывается узким, но полностью доказанным набором свойств.

§ 9Этап 2

Этап 2 — измерить, сломать, удержать

Месяц второй меняет роль: из автора кода вы становитесь его скептиком. Ничего нового не строится — берётся уже работающая система и выясняется, где у неё предел и во что она обходится хозяину.

Направление A

Пропускная способность и латентность

Нагрузка k6 по бизнес-эндпоинту, отдельно — измерение сквозной задержки «коммит → потребитель получил».

  • p50 / p95 / p99 сквозной задержки, а не среднее
  • Предел релэя в событиях/сек и что упирается первым
  • Влияние batch-size и poll-interval на пару «задержка / нагрузка на БД»
Направление B

Профилирование JVM

JFR и async-profiler по работающему стенду, флеймграфы на CPU и на аллокации.

  • Где реально уходит время: сериализация, JDBC, продюсер
  • Аллокации на событие и давление на GC
  • G1 против ZGC на этом профиле нагрузки
Направление C

Virtual threads

Релэй на пуле платформенных потоков против релэя на виртуальных потоках.

  • Гипотеза: выигрыш есть, потому что нагрузка — сплошное блокирующее I/O
  • Поиск pinning: synchronized в драйвере и пуле соединений
  • Размер пула соединений по закону Литтла вместо подбора наугад
Направление D

Хаос и удержание

Toxiproxy между приложением и зависимостями, затем автоматизация проверок в CI.

  • Задержки, разрывы, частичная недоступность брокера
  • Поведение при рестарте пода в середине пачки
  • CI-гейт: PR с просадкой p99 не проходит

Гипотезы, которые проверяются

Правильный способ вести этап 2 — записать предсказание до замера. Совпало — понимание есть; не совпало — вот это и есть самое ценное содержимое второго демо.

Сценарий демо

Второе демо строится вокруг цифр, а не вокруг кода. Таблица гипотез с колонкой «подтвердилось / нет», два-три флеймграфа с указанием, что именно на них видно, график компромисса batch-size, и финал — открытый PR, который CI отклоняет с сообщением о просадке p99. Последнее особенно хорошо смотрится: видно, что результат работы закреплён и не разъедется.

Почему это ценно лично

Профилировать чужой сервис — гадание. Профилировать свой — обучение: вы можете предсказать результат заранее и узнать, ошиблись ли. Именно поэтому измерение идёт вторым этапом, а не первым.

§ 10Рамки

Что вне рамок и какие риски приняты

Вне рамок сознательно

  • Другие брокеры. Только Kafka. Абстракция ради абстракции добавит интерфейсов и уберёт время на измерения.
  • Другие СУБД. Только PostgreSQL: решение опирается на SKIP LOCKED и частичные индексы.
  • Реестр схем и эволюция контрактов. Отдельная большая тема; в стартере payload — просто JSON.
  • Saga и оркестрация процессов. Соблазнительно, но это надстройка над надёжной доставкой, а не её часть. Кандидат в отдельный проект.

Постановка задачи

Разработать переиспользуемый Spring Boot стартер, реализующий паттерны Transactional Outbox и Idempotent Consumer для связки PostgreSQL + Kafka, с демо-стендом и набором нагрузочных и хаос-тестов, подтверждающих заявленные гарантии доставки. Реализацию выполнить на Java, полностью используя средства автоматизации программирования (Codex): декомпозиция задачи под агента, ревью и отладка сгенерированного кода.

Польза для компании

Потеря событий при dual-write — дефект, воспроизводящийся в любом сервисе, который меняет состояние в БД и уведомляет об этом остальных. Обнаруживается он поздно и разбирается вручную: расхождения сверяются по логам, состояние правится точечными запросами. Стартер подключается зависимостью и убирает этот класс дефектов целиком; перф-стенд и методика замеров дальше переиспользуются любой командой для собственных сервисов.

Личное развитие

Семантика доставки Kafka, партиционирование и гарантии порядка, консьюмер-группы и ребалансы. PostgreSQL: уровни изоляции, MVCC, SKIP LOCKED, частичные индексы, autovacuum на таблицах с высоким churn. Проектирование отказоустойчивых компонентов: аренда, идемпотентность, экспоненциальные повторы, DLQ. Testcontainers и Toxiproxy для воспроизводимого хаос-тестирования. Профилирование JVM через JFR и async-profiler, чтение флеймграфов, поведение сборщиков мусора. Виртуальные потоки Project Loom и диагностика pinning. Методика нагрузочного тестирования: перцентили вместо средних, закон Литтла, JMH.

Соответствие KPI

Осязаемость — публикуемый артефакт после каждого этапа. Тиражируемость — библиотека плюс README, подключается без автора. Актуальность — дефект есть в любом событийном сервисе. Качество защиты — оба демо построены на живых экспериментах, а не на слайдах.
