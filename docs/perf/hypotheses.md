# Гипотезы этапа 2

Предсказания зафиксированы до любых performance-замеров. Исходная версия: `stage-1-demo`.
H4 исключена: Bloom-фильтр не обеспечивает корректную дедупликацию и удалён из дизайна.

| № | Предсказание до замера | Факт | Объяснение |
|---|---|---|---|
| H1 | JDBC займёт больше половины активного времени relay в wall-профиле; Kafka CPU будет меньше JDBC. CPU-профиль сам по себе не измеряет ожидание I/O. | Ожидает измерения | Сопоставить CPU, wall, JFR и pg_stat_statements; не включать idle poll в знаменатель активной работы. |
| H2 | При одинаковых двух воркерах и Hikari=10 виртуальные потоки дадут менее 10% выигрыша: число конкурентных запросов не меняется. Увеличение Hikari до 20 может помочь HTTP, но не гарантирует выигрыш relay. | Ожидает измерения | Проверить platform/virtual × Hikari 10/20 при одинаковой нагрузке. |
| H3 | Большая пачка снизит claim/ack запросы на событие. На разреженной нагрузке p99 главным образом определит poll interval; увеличение batch не обязано монотонно повышать p99. | Ожидает измерения | Сетка batch {16,64,128,512} × poll {50,200,1000 ms}; считать реальные SQL-вызовы и e2e histogram. |
| H5 | На двухчасовом прогоне с retention SENT=30s autovacuum будет удерживать dead tuples, но размер таблицы не обязан уменьшаться; первым пределом ожидается CPU/SQL, а не autovacuum. | Ожидает измерения | Два часа, неизменная нагрузка, pg_stat_user_tables, relation size, очередь, e2e p99. V3 добавлять только при доказанной пользе. |

Каждая короткая конфигурация измеряется трижды после 60 секунд прогрева. В отчёте — медиана и min/max,
а не лучший прогон. Базовая лестница: 100/300/500/1000 rps, по 180 секунд на ступень.
Длительные прогоны не совмещаются с другими нагрузками на этот же стенд. Двухчасовые наблюдения
H5 повторяются три раза, если из них делается сравнительный performance-вывод; один полный прогон
служит проверкой устойчивости, а не оценкой разброса.

Цели дизайна: e2e p99 <1.5s, relay >3000 событий/s, HTTP p99 overhead <5%, потери при сбоях =0.
Недостижение цели фиксируется как результат, а не исправляется заменой данных или порога.
