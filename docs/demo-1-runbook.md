# Демо этапа 1 — 15 минут

Подготовка: JDK 21, работающий Docker, `./gradlew build`, `make infra-up`.
Проверенные результаты — [demo-1-results.md](demo-1-results.md); детали реализации —
[implementation-notes.md](implementation-notes.md). Сценарии сбрасывают только данные демо-проекта,
поэтому до показа сохранить нужные результаты. Каждый сценарий сам собирает jar и останавливает
свои JVM после сверки; в терминалах не должно быть дополнительных `bootRun` этих сервисов.

Открыть Grafana `http://localhost:3000/d/reliable-messaging` и Jaeger `http://localhost:16686`.
Поставить Grafana на последние 15 минут. Порты 8081/8082/8083/8085 должны быть свободны.

| Время | Команда / экран | Что объяснить и проверить |
|---|---|---|
| 0:00–1:30 | design.html, диаграмма claim → send → ack | Коммит DB отделён от сети; аренда и токен заменяют удержание блокировки |
| 1:30–3:30 | `make demo-kill9-naive` | 500 rps / 30s; процесс погибает через 10s. Заказ уже закоммичен, асинхронная отправка может пропасть. Сверка должна показать заказы без платежа |
| 3:30–5:30 | `make demo-kill9` | Тот же сбой. Заказы = уникальные order_id = платежи, пропусков и дублей эффекта 0 |
| 5:30–8:00 | `demo-stand/scripts/scenario-kafka-down.sh 1`, Grafana | Пока Kafka выключена, HTTP принимает заказы, pending и возраст растут. После подъёма очередь падает к нулю. Полный пяти­минутный прогон уже сохранён в отчёте |
| 8:00–10:00 | `make demo-three-relays` | Три JVM над одной outbox; искусственно истекают первые аренды. Доставок больше уникальных message_id, но платежей ровно столько, сколько заказов |
| 10:00–11:30 | `make demo-replay` | Оффсеты сброшены к началу: доставок становится больше, число платежей сохраняется |
| 11:30–13:00 | Jaeger → order-service → trace `http post /orders` | В одном trace два сервиса: HTTP-запрос и `orders.v1 receive`; контекст пережил outbox и Kafka |
| 13:00–15:00 | README, таблица гарантий; `make demo-rollback` при наличии времени | Однократность касается одной DB-транзакции и retention inbox. Порядок и внешние HTTP-эффекты не покрываются; DEAD требует разбора |

Ожидаемые ошибки HTTP во время kill/restart не считаются потерей сообщений: сверяем закоммиченные
заказы, а не все попытки отправки запроса. Naive-сценарий возвращает успех, когда обнаружил ожидаемую
потерю; обычный `reconcile.sh` при такой потере возвращает 1.

## Запасной план

Если Docker/JVM/порты не готовы, показать сохранённые таблицы из `demo-1-results.md`, скриншот
роста/дренажа `demo-1-evidence/grafana-kafka-down.jpg` и trace `demo-1-evidence/jaeger-trace.jpg`.
Это результаты настоящего прогона, а не нарисованные примеры. Логи текущих сценариев находятся
в `demo-stand/.run/`; тестовые отчёты — `outbox-spring-boot-starter/build/reports/tests/test/`.

Для полной репетиции с чистыми томами проекта:

```bash
demo-stand/scripts/verify-stage-1.sh
```

Runner не вызывает глобальный `docker volume prune`. Перед удалением томов сохраняет SQL-дампы
демо-баз, если они запущены. Он останавливается на первом неожиданном результате, а полный отчёт
генерирует в `docs/demo-1-results.md` только после успешного завершения всех сценариев.
