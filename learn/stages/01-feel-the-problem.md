# Этап 1 · Почувствовать проблему

**Время:** 1–2 вечера · **Код:** `learn/shop/` · **Тег в конце:** `learn-stage-1`

## История

Сервис заказов принимает заказ, сохраняет его в PostgreSQL и сообщает об этом в Kafka.
Сервис платежей читает сообщение и списывает деньги. Код на первый взгляд очевиден:

```
сохранить заказ в БД
отправить OrderPlaced в Kafka
```

Проблема в том, что это две разные системы, и общей транзакции у них нет. Между двумя строками
есть момент, когда одна запись уже случилась, а вторая ещё нет. Если процесс умрёт именно там —
`kill -9`, OOM, деплой, выдернутый кабель, — системы разойдутся:

- **заказ есть, события нет** — заказ навсегда висит неоплаченным, и никто об этом не узнает;
- **событие есть, заказа нет** — платёжный сервис списал деньги за заказ, которого не существует.

Переставить строки местами не помогает: окно просто переезжает в другое место. На этом этапе
я не чиню это, а **добиваюсь, чтобы оно сломалось у меня на глазах**, и считаю потери.
Весь outbox — ответ на эту поломку, и без неё он выглядит как лишняя сложность.

## Что получится в конце

- Маленький сервис `shop` с одним эндпоинтом `POST /orders`, который пишет в БД и в Kafka «наивно».
- Таблица экспериментов: в каком варианте, при каком сбое, сколько заказов и сколько событий.
- Файл `learn/decisions.md`: почему не подходят очевидные решения, что строим, чего не строим.

## Предсказание

Заполнить **до** того, как писать код. Потом не исправлять — только дописывать факты рядом.

> - Если отправлять в Kafka внутри `@Transactional`-метода, а потом метод бросит исключение, то…
> - Если отправлять после коммита, а процесс убить между коммитом и отправкой, то…

## Проектирование: что делаем, чего не делаем

На этом этапе проектирование — это решить, **какой минимальный код нужен, чтобы увидеть поломку**.

| Делаем | Не делаем и почему |
|---|---|
| Spring Boot, `JdbcTemplate`, `KafkaTemplate` — как в реальном сервисе | JPA — лишняя магия, которая прячет момент коммита |
| Одна таблица `orders`, Flyway | Валидацию, DTO-слои, обработку ошибок — к проблеме не относятся |
| Ручку «сломать здесь»: искусственное исключение и задержку в опасном месте | Получателя — посчитать сообщения в топике можно без него |
| Сообщение в виде JSON-строки | Схемы, Avro, заголовки — понадобятся позже |

Вопрос, на который надо ответить перед кодом: **где именно находится момент коммита
транзакции** в Spring-методе с `@Transactional`? От этого зависит, куда ставить задержку.

<details><summary>Подсказка</summary>

Коммит происходит не на последней строке метода, а после выхода из него — в прокси,
который Spring обернул вокруг бина. Значит, код «после коммита» внутри того же метода
напрямую не написать. Есть два пути: вызвать отправку снаружи транзакционного метода
или зарегистрировать колбэк «после коммита».
</details>

## Исполнение

### Шаг 0 · Проект

Сгенерировать проект на [start.spring.io](https://start.spring.io) и распаковать в `learn/shop/`.

- Gradle – Kotlin, Java 21, Spring Boot **3.5.x** — та же линейка, что у стартера.
- Group `dev.learn`, artifact `shop`.
- Зависимости: Spring Web, JDBC API, PostgreSQL Driver, Spring for Apache Kafka, Flyway Migration.

Порт сервиса — `8090`, чтобы не пересекаться с демо (8081/8082).

<details><summary>Если 3.5.x на сайте уже не предлагается</summary>

Сгенерировать с любой версией и в `build.gradle.kts` вручную поставить версию плагина
`org.springframework.boot` из `gradle/libs.versions.toml` корня репозитория. В Boot 4 часть
стартеров переименована, поэтому имена зависимостей сверить с `demo-stand/order-service/build.gradle.kts`
— это build-конфиг, а не логика, смотреть можно.
</details>

**Проверка шага:** `./gradlew bootRun` в `learn/shop/` стартует и падает только на подключении к БД.

### Шаг 1 · База и схема

Создать базу `shop` рядом с базой демо:

```bash
make infra-up
docker compose -f demo-stand/docker-compose.yml exec order-postgres createdb -U orders shop
```

Дальше самому: настройки подключения в `application.yml` (хост `localhost:5433`,
пользователь и пароль `orders`) и первая миграция с таблицей `orders`.

<details><summary>Подсказка 1 — что должно быть в таблице</summary>

Минимум: идентификатор, клиент, сумма, время создания. Идентификатор лучше генерировать
в приложении (`UUID`), а не в базе — он понадобится как ключ сообщения в Kafka ещё до вставки.
</details>

<details><summary>Подсказка 2 — куда класть миграцию</summary>

Flyway по умолчанию ищет `src/main/resources/db/migration/`, имя файла вида `V1__orders.sql`.
Два подчёркивания обязательны.
</details>

<details><summary>Подсказка 3 — синтаксис настроек</summary>

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5433/shop
    username: orders
    password: orders
server:
  port: 8090
```
</details>

**Проверка шага:** приложение стартует, в логе Flyway видно `Successfully applied 1 migration`.

### Шаг 2 · Наивная запись, вариант А: отправка внутри транзакции

**Контракт**
- `POST /orders` с телом `{"customerId": "...", "total": 42.50}` возвращает `201` и id заказа.
- В одном `@Transactional`-методе: строка в `orders` и JSON-сообщение в топик `shop.orders.v1`,
  ключ сообщения = id заказа.
- `POST /orders?fail=true` бросает исключение **после** отправки — имитация того, что
  транзакция откатилась, когда событие уже ушло.

<details><summary>Подсказка 1 — из каких частей состоит</summary>

Контроллер → сервис с `@Transactional` → `JdbcTemplate.update(...)` и `KafkaTemplate.send(...)`.
Событие — `record` с полями заказа, в строку его превращает `ObjectMapper`, который Spring
уже создал как бин.
</details>

<details><summary>Подсказка 2 — какие настройки нужны Kafka</summary>

`spring.kafka.bootstrap-servers` и сериализаторы ключа и значения — `StringSerializer` для обоих.
Топик Kafka на демо-стенде создаст сама при первой отправке.
</details>

<details><summary>Подсказка 3 — синтаксис API</summary>

```java
jdbc.update("insert into t(a, b) values (?, ?)", a, b);

CompletableFuture<SendResult<String, String>> f = kafka.send("topic", key, json);
f.get(); // если нужно дождаться подтверждения брокера

String json = mapper.writeValueAsString(object);
```

```yaml
spring:
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.apache.kafka.common.serialization.StringSerializer
```
</details>

### Шаг 3 · Видеть оба мира

Без способа посчитать обе стороны эксперимент не провести. Эти команды — инструмент,
а не решение, поэтому даны целиком. Имеет смысл сложить их в свой `learn/shop/count.sh`.

```bash
# Заказов в БД
docker compose -f demo-stand/docker-compose.yml exec order-postgres \
  psql -U orders -d shop -tAc 'select count(*) from orders'
```

```bash
# Сообщений в топике: сумма конечных оффсетов по партициям
docker compose -f demo-stand/docker-compose.yml exec kafka \
  /opt/kafka/bin/kafka-get-offsets.sh --bootstrap-server localhost:9092 --topic shop.orders.v1
```

```bash
# Сами сообщения, с ключами
docker compose -f demo-stand/docker-compose.yml exec kafka \
  /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic shop.orders.v1 --from-beginning --property print.key=true --timeout-ms 5000
```

Чтобы начинать каждый эксперимент с нуля: `truncate orders` в БД и удаление топика
(`kafka-topics.sh --delete --topic shop.orders.v1`). Либо просто записывать счётчики до и после.

### Шаг 4 · Эксперименты

Каждый эксперимент: записать предсказание в журнал → запустить → посчитать обе стороны → записать факт.
Здесь код меняется понемногу, а главное — что увидишь. Таймбокс 15 минут на шаг по-прежнему действует.

**Э1. Откат после отправки (вариант А).**
`POST /orders?fail=true`. Что в БД, что в топике?

**Э2. Смерть между коммитом и отправкой (вариант Б).**
Переделать сервис так, чтобы отправка шла **после** коммита. Добавить настраиваемую задержку
перед отправкой, например `shop.chaos.delay-before-send: 10s`. Отправить заказ и во время
задержки убить процесс по-настоящему:

```bash
kill -9 $(lsof -tiTCP:8090 -sTCP:LISTEN)
```

<details><summary>Подсказка 1 — как отправить после коммита</summary>

Два варианта: контроллер сначала вызывает транзакционный метод, потом отправляет; или внутри
транзакции зарегистрировать колбэк, который Spring вызовет после коммита. Второй вариант
ближе к тому, что делает эталонный наивный режим, и интереснее: стоит понять, почему.
</details>

<details><summary>Подсказка 2 — синтаксис колбэка после коммита</summary>

```java
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override
    public void afterCommit() {
        // выполнится после успешного коммита текущей транзакции
    }
});
```

Альтернатива — опубликовать Spring-событие и поймать его методом с
`@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`.
</details>

<details><summary>Подсказка 3 — задержка из настроек</summary>

```java
public Orders(..., @Value("${shop.chaos.delay-before-send:0s}") Duration delay) { ... }
Thread.sleep(delay);
```
</details>

**Э3. Kafka лежит (вариант Б).**

```bash
docker compose -f demo-stand/docker-compose.yml stop kafka
```

Создать заказ. Что вернул HTTP? Что в БД? Что в логе приложения и через сколько? Потом поднять
Kafka обратно (`start kafka`) — доедет ли событие? Повторить, дожидаясь подтверждения через `.get()`:
что изменилось в ответе HTTP и что **не** изменилось в БД?

По умолчанию продюсер ждёт до минуты-двух, прежде чем сдаться. Чтобы не ждать:

```yaml
spring:
  kafka:
    producer:
      properties:
        max.block.ms: 3000
        request.timeout.ms: 3000
        delivery.timeout.ms: 5000
```

**Э4 (бонус). Синхронная отправка до коммита (вариант А + `.get()`).**
Вернуться к отправке внутри транзакции, дождаться подтверждения от брокера, затем задержка
**перед коммитом** и `kill -9` во время неё. Это ответ тем, кто говорит «просто дождитесь ack».

**Э5 (бонус). Без искусственной задержки.**
Убрать задержку, дать нагрузку и убить процесс посреди неё. Получится ли поймать потерю
«естественно»? Если нет — почему эталонный сценарий `kill -9` гоняет 500 запросов в секунду?

```bash
seq 1 5000 | xargs -P 20 -I{} curl -s -o /dev/null -X POST localhost:8090/orders \
  -H 'content-type: application/json' -d '{"customerId":"c-{}","total":1.00}'
```

### Шаг 5 · Проектирование следующего шага

Теперь, когда поломка увидена, — решить, что с ней делать. Создать `learn/decisions.md` и
для каждого очевидного решения записать одной-двумя фразами, **в какой момент оно ломается**.
Если не получается сформулировать — это и есть то место, которое надо проверить экспериментом.

| Идея | Где ломается |
|---|---|
| Повторять отправку в цикле, пока не получится | |
| Отправлять синхронно до коммита и ждать ack | (см. Э4) |
| Включить Kafka-транзакции и коммитить обе транзакции подряд | |
| Распределённая транзакция XA / 2PC | |
| Сначала писать в Kafka, а БД обновлять своим же консьюмером | |
| CDC: читать журнал PostgreSQL (WAL) внешним процессом | |
| Писать событие строкой в ту же БД, отправлять отдельным процессом | |

Потом — одностраничник «что строим» для фазы 1. Вопросы, на которые он отвечает:

1. Какую гарантию доставки даём: *at-most-once*, *at-least-once*, *exactly-once*? Почему не третью?
2. Если *at-least-once*, то где появятся дубли и кто за них отвечает?
3. Обещаем ли порядок событий одного заказа? (можно оставить открытым — вернёмся в этапе 3)
4. Что точно **не** делаем в фазе 1: производительность, CDC, saga, однократность внешних HTTP-вызовов.
5. Критерий успеха этапа 2: какие из экспериментов Э1–Э4 должны дать расхождение 0?
